# ShiftLead — design history

The dated record of how [`design.md`](design.md) came to say what it says: decisions, reversals,
review rounds, live findings and Paul's words, by section, in date order. `design.md` is the
present-tense specification and states only what is true now; this file is where its history went
on 2026-09-22 (the design review, TD-109) and where every later change appends its dated fact.
Nothing here is a rule. Where a bullet and the design disagree, the design is current and the
bullet is what was true on its date.

The ADRs under [`decisions/`](decisions/) and the ledger ([`technical_debt.md`](technical_debt.md),
[`technical_debt_archive.md`](technical_debt_archive.md)) hold the reasoning behind the larger
decisions; this file points at them rather than repeating them.

## 4.1 Session substrate: tmux, one session per conversation

- undated (PR #17): Resume's supersede — closes the exited record and keeps it a day. The create-time supersede (below) extends it to a fresh start under the same name and goes one step further by forgetting rather than keeping.
- undated: `pipe-pane` continuous streaming to `~/.agentorc/runs/<session>-<created>.log` replaced tdgrind's per-tick snapshot.
- 2026-09-10 (§10 decision, §9 invariant 12): a name identifies one session within its scope (the repo, or the directory for a repo-less session).
- 2026-09-10 (TD-010 a): a live session with no tmux at all (`claude` in a VS Code terminal, found via Claude Code's registry `~/.claude/sessions/<pid>.json`) was shown as a read-only card.
- 2026-09-10 ([ADR herdr spike](decisions/2026-09-10-herdr-spike.md)): measured on herdr that a runtime holding the ptys itself must kill every session to restart and re-launch the tool with `--resume` once a client attaches — the reason tmux owns the processes; the same spike saw a `.bashrc` `cd` relocate every pane — the reason argv runs directly, never through the person's shell.
- 2026-09-11 (TD-030, all of it): every `ao` subcommand that takes an id accepts a bare name ("so nothing that worked before changes" — a full `ao-…` id still means itself); the create-time name rules landed: live holder refused with error data, exited/closed holder superseded and replaced in place with *previous run* as a new field, unrecorded tmux panes decided on tmux's own answer, the check locked on the scope. What was wrong before: the same `ao new` would refuse or suffix depending on the second it landed in (whether the tick had adopted a stale pane), and `-2` cards appeared for a name that was simply reused.
- 2026-09-13 (TD-036 step 1): the `controllers` field landed (§4.8's membership list).
- 2026-09-13: `team` and `project` badges landed (§4.9).
- 2026-09-17: Paul had the no-tmux read-only cards (TD-010 a) removed — a card for a session a person started by hand, outside agentorc, reads as being watched, and it offered nothing to do. The Org is what agentorc started or adopted; the registry is still read only for `occupancy` (§9 invariant 2).
- 2026-09-20 (TD-077 a2): the suspended exception designed and built — a holder a person suspended over an identity alarm refuses every `create` under its name until a person lifts it; the name check answers `suspended`.
- 2026-09-20: a team would not start because a brief had reached 16,194 bytes and tmux refused the argv ("command too long", about 16 KB). Fix: past 8 KB the argv goes to `launch/<tmux name>.sh` (mode 0700) exec'd under `/bin/sh` — the one exception to argv-runs-directly.

## 4.3 Adapter contract

- 2026-09-13: the word *turn* was taken from OpenAI's Agents API (ADR decisions/2026-09-13-openai-agents-api.md) because it named a split agentorc already had and could not say in a sentence: session durable, turn one piece of work. Send to `idle` starts a turn, to `working` steers it — one control, not two, because the difference is what the person is doing, not what the code does.
- 2026-09-14 (§4.10): `mail()` added to the adapter protocol; when an adapter has no native delivery path the core falls back to a pane write (a `send`), and §4.10's message/control line becomes a convention the adapter's brief keeps rather than a gate the host agent enforces.
- The adapter status table was written "at design time", each row to be verified before its adapter is built; Claude Code and `shell` were phase 1.
- 2026-09-23 (TD-122): `label` added to the contract (the tool's display name, for the chip), and `usage()` said to be called once per account and to carry every window the endpoint reports, a per-model weekly one labelled with the model.
- 2026-09-23 (TD-122, the build): `account_for(profile)` added to the contract as an optional method — the core cannot read a profile, so the adapter says which account the poll keys on; without it the poll keys on the profile, as before.
- 2026-09-24 (TD-035, the designer): the 2026-09-12 decision with Paul — tool-specific wiring of a repo's start hooks belongs in the adapter, not in the repo — written into the contract as *A repo's start hooks are every adapter's to run*: through the tool's start hook, else the runner at launch with its stdout prepended to the first prompt; the anchor check's source for another tool decided with that adapter (TD-112). Nothing to build until a second adapter exists.
- 2026-09-25 (TD-128, the designer): `spend(profile)` — per-turn tokens and cost from the tool's own records for a metered profile; the prices are the profile's, never the core's.
- 2026-09-25 (TD-128 reconciled, with Paul): `spend(profile, cursors)` with four token kinds — cache reads folded into input would report a bill several times the real one — read from a byte cursor per transcript across the profile's config directory, sessions agentorc did not start included.
- 2026-09-25 (TD-154, the designer): `read_transcript` joined the contract beside `transcript_path` — the adapter renders its file into neutral entries and the core draws them, so a second adapter's transcript draws on the same page.
- 2026-09-26 (TD-188, the designer): `context` on the contract — the session's context size from the tool's records, Claude Code's from the last assistant entry's `usage`.
- 2026-09-27 (TD-190 slice 1, grinder-ao-1): `context()` is built as `{tokens, at, window}` keyed by the profile *name*, the shape `model_in_use` already had, where the design of 2026-09-26 wrote a `Context` type and a `Profile` argument: the core cannot build a `Profile` (it lives in `agentorc`), and every optional method the core calls takes the name. The windows are a table of model-id prefixes in the adapter: 1M for the Fable, Mythos, Opus 5 and 4.6–4.8 and Sonnet 5 and 4.6 families, 200k for Haiku 4.5, none for anything else.

- 2026-09-27 (TD-151 slice 2, grinder-ao-1): Claude Code's `spend` built — every transcript under the profile's config directory read from its cursor to its last whole line (a line still being written waits), subagents' transcripts included, a cursor past the end read from 0. Two things the build decided: the result is `{turns, cursors, reason}` — the design's pair with the reason beside it, as `usage_for` carries one; and one API response is one turn, because Claude Code writes a response as one entry per content block, each carrying the response's usage — a read keeps the last entry per `message.id`, so a response whose entries straddle two reads would be counted twice, which slice 3's ledger is to guard against. From the review of #674: a metered profile must name a `config_dir` of its own, shared only within its account, or `profiles.yml` refuses it — reading the tool's default directory would bill a subscription's turns to the key.

## 4.4 Host agent

- 2026-09-26 (TD-176 slice 1, built): the repo facts' PR read became **two reads** — the open list, and every PR updated in the last month with a limit of 1000 — because this repo opens about forty PRs a day and the designed `--limit 200` page covered five days of a month's window. The windows became **rolling** (the last day, 7 and 30 days) where the design had said *in the home's clock*: a calendar week read near zero every Monday morning, which is not the balance question the counts answer. The history is read with `--first-parent`, so a merged branch's own commits never open and close an entry twice.
- 2026-09-28 (TD-223 and TD-198, the designer; Paul the same day: *should we consider retiring "pickable" and using ledger.py to determine it based on "blocked by" instead?*): **pickable became derived** in the ledger reading — cadence §2.4's rule, the one dev-cadence's `scripts/ledger.py` applies — and the written `**Pickable:**` line (TD-118) retires. It had been read as written, so dev-cadence's ledger, which writes no header lines, read `pickable: ''` throughout: rule 6 matched nothing there, and grinder-dc-1 sat idle beside a pickable TD-070. The reader is agentorc's own and a test holds it equal to the repo's script: running a repo's script from the home, the entry's option (a), was turned down because the home would run a repo's code on every ledger change and a repo without the script would read nothing. The page's kinds are tested *for you*, *design-first*, *pickable*, *other*: *pickable* had won and counted 7 designer entries among 19 (TD-198). From the fact-check, run on the ledger of that day: removing the lines as first written would have turned about thirty entries pickable, the anchor's among them, so the migration gives each written *no* a `Kind:`, an `Owner:` or a `Blocked by:` first and shows each lane's matches unchanged. Build: TD-228.
- 2026-09-26 (TD-176, with Paul): **Repo facts** widened — PRs read with `--state all` and counted *opened* / *closed* per window; the ledger's *opened* / *closed* per window from the file's git history; the four kinds (for you = `Owner: paul` or `Kind: decision`); the phases derived on the view; and the **doing log**, the last fifty `doing` calls per team, `doing.jsonl`, the `doing` RPC and event.
- 2026-09-25 (TD-176, in a cloud session with Paul): **Repo facts** — open PRs by `gh pr list --state open` every five minutes per remote and the ledger's entry headers by a `sessionorc.ledger` reader, kept in `repos.json` and pushed as a `repos` event; an outage keeps the last reading and says so, the seat counter's rule. Board counts stay with the board reader the Inbox already runs.
- Until 2026-09-20 the usage poll ran every minute; TD-087 moved it to five minutes because a minute buys nothing against a five-hour window while spending an allowance the tool itself shares. The stated cost: a session at its cap shows `limited` up to five minutes later rather than up to one.
- 2026-09-20 (TD-087): usage fetch failures gained a reason. Before, *rate-limited*, *no credentials*, *no network* and *no profile* were one silence, and the silence cost more than a missing chip: `limited` is read from the same reading, so a session at its cap was not marked while the endpoint refused us. The `Retry-After` from a 429 is honoured uncapped because "a server saying *an hour and a half* knows something our ceiling is guessing at"; our own doubling stops at an hour.
- 2026-09-20 (TD-087): the usage reading moved to `usage.json`. It had lived in memory, so each promote forgot it and polled at once — eight times in one day. The first poll after a restart now waits until the held `fetched` plus the cadence.
- 2026-09-28 (TD-231 and TD-230, the designer; Paul: *our percentage used for the claude sub seems to be stale — our page reads 88%/95% but actual is 93% used*, *add how long ago the reading was made in the display*, *investigate the 429s*): usage became **reported first and asked for last**. Until then the one source was a poll of the tool's undocumented usage endpoint, every five minutes per account, and on 2026-09-28 it was refused for six hours: the held reading stood at 88% while the account was at 93%, the chip said *stale* and not how stale, and the gate, reading the same number against a line of 95%, could see no crossing. The anchor's research that day found no documented way to read a subscription's limits but the status line's `rate_limits`, and found the 429s widely reported with no usable `Retry-After`. So a session's status line reports what it is told, the endpoint is asked only for an account with no reading under fifteen minutes old and left alone an hour after a refusal, every reading carries its age, and the gate projects a reading older than `max_age` from the rate it last saw, pausing on the projection and resuming only on a reading. From the fact-check, which read the tool's documentation of the status line: a redraw repeats the last numbers, so reports are merged by what a window can do and a report's age moves only when the session has had a response; a pause on a projection must be able to end without a report, since paused sessions send none; `max_age` is a key of its own, `usage:`, because every key under `usage_gate` is a profile's name. Turned down: the rate-limit headers on model responses (undocumented), and asking the person each time a reading goes old (a night's question nobody is awake for). Build: TD-233.
- 2026-09-29 (TD-233 slice 3, grinder-ao-1): the usage endpoint became the fallback it was designed as. Until this date the host agent asked each account every five minutes and, after a 429, waited the endpoint's `Retry-After` floored at five minutes or doubled to an hour; on 2026-09-28 the endpoint refused for six hours with `Retry-After` 0 or none, so the doubling learnt nothing. Now an account is asked only when its reading is older than `USAGE_FRESH` (fifteen minutes) and at most once per `USAGE_FRESH`, and a 429 cools it off for `USAGE_COOL`, a fixed hour, a longer `Retry-After` kept; its end rides on the reading as `cool_until`, since the review found that a promote inside the hour would otherwise ask at once from the held reading's old `fetched`. `USAGE_EVERY` and `USAGE_BACKOFF_MAX` went. Until the report (slice 2) exists this is a fifteen-minute poll; the hourly ask for a window only the endpoint gives waits for the report, since until then every window comes from the same ask. Already true and not changed: each host asks for its own sessions' profiles, and `limited` skips a window past its reset.
- 2026-09-29 (TD-233 slice 2, the host agent's half, grinder-ao-1): the `usage_report` RPC, `sessionorc.usage` (the merge, the history, the hourly ask for a window only the endpoint gives) and each window's own `at`, `source` and `history` in `usage.json`. Two choices the design left open, written into §4.4 *The reading*: the endpoint's answer sets the windows it names outright, since it is the account's own number and a stale high report must not outlive it — the merge by the highest applies to reports; and two resets within five minutes are one window, since the status line's epoch seconds and the endpoint's instant never quite agree and a rolling window drifts. The caller of the RPC is the session the envelope names, so the identity check covers it as any other method.
