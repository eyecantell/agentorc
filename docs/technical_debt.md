## TD-005: `pretrust()` can lose a concurrent Claude Code rewrite of `.claude.json`

**Priority:** Low
**Added:** 2026-09-06
**Status:** Open
**Location:** `src/agentorc/adapters/claude_code/__init__.py` (`pretrust`)

**Why:** The first-run trust quirk does a read-modify-write of Claude Code's own `.claude.json` under an flock that only agentorc takes. A running Claude Code session that rewrites the file inside that window loses its write (or we lose our flag, which merely re-shows the dialog). Raised in the PR #3 review; the window is one read plus one write at launch time.

**Fix:** either watch for the dialog in the pane as the fallback and answer it through the terminal channel, or find a supported way to pre-trust a directory (a `--trust`-style flag or a per-project settings key) and drop the file edit. Done when no agentorc code writes `.claude.json`.

**Related:** TD-006.

## TD-026: Scheduling: start/stop times and window overrides for unattended sessions, editable from the UI

**Priority:** Medium
**Added:** 2026-09-10
**Status:** Partly done — the per-session **stop time** landed 2026-09-13 (PR #129): `run_until` on the record, `ao new --unattended --until 06:00|+8h|<ISO>`, `ao until <session> <when>|--clear`, the wrap-up-then-kill on the tick, and *stops 06:00* on `ao status -v`. That closes gap (1) below — a hand-started worker now has a stopper. Open: `start_at` and the `scheduled` state, window overrides with an expiry, calendar-shaped schedules, one-off runs, and the UI *beyond* the stop time — the card and Focus header say *stops 06:00* and the New session form has an **Until** field (PR #131), **and the Focus header's badge became the control that edits it on 2026-09-14 (PR #147)** — click for a time, empty to clear, drawn only for an unattended session since the agent refuses one on an interactive session either way; a session with no stop time shows a dim *no stop time* rather than nothing, because "nothing will stop this" is the fact a person opening Focus most needs. The review of that PR found a live bug the control would have made easy to hit: `set_stop` cleared `wrapup_sent_at` on every call, so re-confirming an unchanged, already-elapsed stop time asked a session inside its wrap-up grace to wrap up a second time — and, since the ask happens before the grace check, repeatedly touching the control deferred the forced kill indefinitely, which is this entry's own gap (1) reintroduced through the edit path. Only a *different* time now counts as a new run. Latent and not reached today: every caller passes the one shared `WRAPUP_PROMPT`, so the control cannot yet clobber a custom wrap-up text, but it would if custom texts were ever exposed. The card shows no next transition for a repo window because there is no repo window. The repo window is still phase 3; when it lands it should *set* a stop time rather than be a second mechanism.
**Location:** design §6 (policies), §4.5a (New session, card / Focus header), §5 `.agentorc.yml` `unattended:` block

**Why:** Design §6 gives unattended sessions one schedule: the repo's weekly `window` (phase 3, the tdgrind port). That covers the nightly grind and nothing else. Two gaps showed on 2026-09-10, the first day the three samscrape tdgrind workers ran under agentorc instead of the cron supervisor: (1) a worker started by hand with `ao new --unattended` outside the window has **no stopper at all** — nothing wraps it up at 06:00, at a usage cap, or when the token lapses, so "start it now so I can watch it" means "remember to close it yourself"; (2) every deviation from the weekly window is a hand edit to a config file — tdgrind's `~/.tdgrind/config` carries dated shell one-liners (`[ "$(date -u +%s)" -lt <epoch> ] && WINDOW_START=0 …`) for "Paul is out today, run all day", which is a schedule expressed as code, invisible to the Team and forgotten once it lapses. A scheduler is the general form of both: a session or repo carries *when it may run*, the policy tick enforces it, and the UI shows and edits it.

**Fix:** treat the weekly window as one kind of schedule and add the others on the same policy tick, all visible on the card:

- **Per-session `run_until` / `start_at`** on the New session form and the `ao new` flags (`--until 06:00`, `--until +8h`, `--at 20:00`): a stop time gets wrap-up-then-kill exactly like leaving the window; a start time queues the session (a new `scheduled` state on the Org page, with the time) and the tick launches it. A session started by hand with `--unattended` and no `--until` inherits the repo window's next close, so gap (1) cannot recur.
  **`--until` landed 2026-09-13 (PR #129)**: the CLI parses `06:00` (the next one, in the caller's local clock), `+8h` and ISO and hands the agent an absolute instant — "the next 06:00" is a question about the caller's clock, so the record never has to answer it. At the instant the agent sends the wrap-up prompt once and kills the session when it settles or ten minutes later; the wording travels on the record (like `ledger`) because `sessionorc` must not know what a brief is, and it is the same text `ao team stop` sends. `ao until <session> <when>|--clear` sets or clears it afterwards, through a `set_stop` RPC gated as an acting call — a stop time is a `kill` with a delay on it. `--until` without `--unattended` is refused rather than stored: a stop time nothing will act on is this entry's own failure inverted. The UI followed in PR #131: the **stops** note on the card and the Focus header (§4.5a), from the same formatter `ao status -v` uses, and the New session **Until** field, which refuses a stop time on a session that is not unattended exactly as `ao new` does. Left here: `start_at`, the `scheduled` state, editing a stop time from the page (the CLI's `ao until` has no page equivalent yet), and the inheritance from the repo window, which needs the window (phase 3) first.
- **Window overrides with an expiry**, per repo, kept in agent state rather than the checked-in `.agentorc.yml`: "run all day until 2026-09-02 20:00", "pause until Monday" (the PAUSE flag with a date), caps to 99% until the weekly reset. Shown on the repo's row with the expiry; expired overrides fall away by themselves. This replaces the dated one-liners in tdgrind's config.
- **Calendar-shaped schedules** in the `unattended:` block beyond weekday/weekend: a list of `{days, hours}` rules, and a `tz` (the window is in the host's local time today, which is right on one host and ambiguous on two — phase 2 adds the second host).
- **One-off runs**: schedule a *command* session (§4.5 Commands) or a brief at a time — "run the deploy at 02:00", "start a review worker Friday evening" — which is the Commands tab plus a time. This is the dev-cadence `/schedule`-style routine, local and tmux-backed.
- Edits from the UI go through agent RPCs (`set_schedule`, `set_override`), never by writing the repo file; the checked-in block is the default, overrides layer on top. `ao status` shows the next transition ("stops 06:00", "starts Fri 20:00") per session and per repo.

Done when: a hand-started unattended session shows when it will stop and stops then; "run all day today" is one click or one `ao` line with an expiry, not a config edit; the Team shows a scheduled-but-not-started session; and tdgrind's `config` overrides file has nothing left to express.

**Related:** design §6 run window / usage gate / PAUSE, §7 phase 3 (tdgrind migration — this is the step after it, or the shape the port should take), TD-010 (adopting hand-started sessions faces the same "who stops it" question), samscrape TD-274 (the tdgrind supervisor), samscrape `~/.tdgrind/config` dated overrides of 2026-09-01.

## TD-046: A session cannot be popped out into its own browser window, so switching between agents needs the mouse

**Priority:** Medium
**Added:** 2026-09-13 (raised by Paul)

**Why:** every Focus opens in the tab you were in, so moving between two working agents is Org → click a card → Focus → back → click the other. One OS window per agent makes the fleet behave like the terminals it replaces: alt-tab is muscle memory, the windows can be tiled or sent to separate monitors, and the terminal keeps its own scrollback and keyboard focus instead of being torn down and rebuilt on every navigation. It also fixes something the current shape cannot: a pane you are watching disappears the moment you look at another one, so there is no way to keep two agents visible at once on one screen.

**Fix (design first, then code), the pieces that need deciding:**

1. **The control.** A **pop out** button on the card's `more ▾` menu and in the Focus header, plus the obvious shortcut of middle-click or ctrl-click on Focus behaving as it already does on a link. §4.5a gains the row; a control not in that table does not exist.
2. **A chromeless route.** `/focus/{sid}?window=1` (or a `/pane/{sid}`) rendering the Focus screen without the nav, so the window is the session and nothing else. Decide whether the side panels come with it.
3. **The window itself.** `window.open` with a **name keyed on the session id**, so pressing pop out twice focuses the window that exists rather than opening a second one. Decide the default size and whether position is remembered per session (localStorage, like Pinned order).
4. **The window title is the point.** It is what alt-tab shows, so it must be the session's name first and short — `tdgrind-ao-1 · working` rather than `agentorc — Focus`. It has to track the state deltas the page already receives, and say when the session needs you, since a window switcher is the only place a background window can speak.
5. **Cost of many windows.** Each tab opens its own `/events` websocket and its own terminal pty (§4.6). 6. **The opener's grid.** A card whose session is popped out should say so and offer *focus that window* rather than a second one, or the person ends up with two views of one pane and no way to tell them apart.

Done when two agents can be open in two OS windows at once, alt-tab moves between them, each window's title names its session and its state, and popping out the same session twice raises the first window instead of opening another.

## TD-050: The cadence check's `review` row reads the verdict only on a comment's first line

**Priority:** Medium
**Added:** 2026-09-14
**Status:** Open — the fix is dev-cadence's (`scripts/check_cadence.py` and `docs/cadence.md` both carry the SYNCED FILE header), so this entry records the finding and the board item asks for the call

**Location:** `scripts/check_cadence.py` (`REVIEW_RE`, the `review` row), `docs/cadence.md` §4 (where the format is given)

**Why:** The row matches `REVIEW_RE` against `body.splitlines()[:1]` — the comment's **first line only**. Every reviewer in this repo is briefed to *end* its report with the verdict line ("End with exactly one line: `cadence-review: …`"), which is the natural place for a conclusion, and a PR comment written that way reads to the check as **no review at all**: the row says "no `cadence-review:` comment on the PR (cadence §4)", which is indistinguishable from never having had one reviewed. There is a second, sharper edge: a merged PR's row cannot be repaired. Editing the comment to move the verdict line makes the check see it and then fail on `updated_at > merged_at` ("review comment edited after the merge"), which is the right answer and still a permanent FAIL. So a session that learns the rule the usual way leaves a red row behind whatever it does.

**Fix:** either (a) `docs/cadence.md` §4 says "the verdict must be the comment's first line" where it gives the format, so the rule is visible where it is read; or (b) `REVIEW_RE` scans the whole body rather than the first line, which costs nothing, removes the trap, and matches how the reports are actually written — with (a) as documentation either way. Preference is (b): the check is a detector, and a detector that misses the evidence in front of it is worse than one that is slightly looser. Done when a review comment ending with its verdict line passes the `review` row.

## TD-058: Stopping the host agent hangs until systemd kills it

**Priority:** Medium
**Added:** 2026-09-16 (observed by the anchor session restarting the units for TD-052's live check)

**Status:** Partly done — **the agent half is fixed 2026-09-17 (PR #176)**: `serve()` no longer awaits `serve_forever()`, whose own cancel path awaits `wait_closed()` before any `finally` of ours can run (closing connections in a `finally` around it still hangs — tried first); it tracks every client connection in `_handle_conn` (`_conns`) and on cancel closes the server and each connection before `async with server` waits, so a blocked `wait` sees the close, is cancelled and writes its cursor. `test_stop_closes_a_subscriber_and_a_blocked_wait` stops an agent holding a subscriber and a 600 s `wait` within a second (unfixed, it hangs). **The UI half is fixed too (PR #177)**: the `/events` handler sat in its agent subscription until the *next* event's send failed, since the page never sends on that socket — and uvicorn's shutdown closes each websocket's transport and then waits for its handler, so the UI stopped whenever something next changed (the 40 s). The handler now races the stream against a watch for the websocket's disconnect and ends on whichever comes first; `test_ui_stop.py` drives the ASGI app against an idle agent and asserts the handler ends, and its agent subscription goes, within 2 s of the disconnect (unfixed, it does not — the TestClient cannot show this, since it cancels a websocket handler on exit). Established by that test, not yet on the live unit. `/term/` needed nothing: its pump reads the disconnect. **Remaining:** (1) the live check in **Done when** below, now for both units (docs/user_attention.md); (2) the `TimeoutStopSec` backstop, not added — consider it only if the live check still shows a slow stop. History — **cause confirmed 2026-09-16 22:36 MDT**: with `agentorc-ui` stopped first (closing its `subscribe` connection) and no `wait` blocked, `systemctl --user stop agentorc-agent` returned in under a second and the journal shows a clean `Stopped`, no timeout and no SIGKILL. The same run found a second, separate hang: `systemctl --user stop agentorc-ui` took 40 s to return, so the UI has a slow stop of its own (open terminal websockets or the agent subscription held through uvicorn's graceful shutdown are the likely holders — not diagnosed). Until this is fixed, stop the UI before the agent **Verified live 2026-09-17 00:41:** with #176 and #177 loaded, `systemctl --user restart agentorc-ui agentorc-agent` returned in under a second with six sessions attached; the restart before it (00:07, old code) took the full 90 s.

**Location:** `src/agentorc/ui/app.py` (the UI's shutdown), `src/sessionorc/agent.py` (`HostAgent.serve`: `async with server: await server.serve_forever()`; `serve_until_signal`), `src/agentorc/service.py` (the unit: `KillMode=process`, no `TimeoutStopSec`)

**Why:** on 2026-09-16 21:24 MDT `systemctl --user restart agentorc-agent` sat in `stop-sigterm` for 90 s, then systemd logged `State 'stop-sigterm' timed out. Killing.` and sent SIGKILL (`journalctl --user -u agentorc-agent`). SIGTERM cancels the serve task (TD-024), and leaving `async with server` calls `Server.wait_closed()`, which since Python 3.12 waits for **every open client connection** to finish — and the UI's `subscribe` connection never does, nor does a CLI blocked in the `wait` RPC (TD-052 step 3, which makes long-lived connections the normal case for every lead). So a stop never completes on its own. Nothing is lost today — tmux holds the sessions, the store is written on every change, and the unit restarts — but the socket file is not unlinked by the `finally`, in-flight permission waiters die without an answer, every restart costs 90 s during which hooks queue to disk, and a SIGKILL is the wrong default for a process that will soon hold the org's mail.

**Fix:** on shutdown, close the client connections the agent holds (subscribers, `_waits`, and any other open writer — track them in `_handle_conn`) before awaiting `wait_closed()`, or bound the wait with a short timeout and then close them; cancel blocked `wait` RPCs so each writes its cursor; keep the `finally` that unlinks the socket reachable. A test: an agent with one subscriber and one blocked `wait` stops within a second of the serve task being cancelled. Consider `TimeoutStopSec=10` on the unit as the backstop, not the fix.

**Done when** `systemctl --user restart agentorc-agent` returns in a few seconds with the UI open and a lead blocked in `ao wait`, and the journal shows a clean stop.

**Related:** TD-024 (archived: the pending-task traceback on SIGTERM, which made the cancel path clean but did not meet this), TD-052 step 3 (the `wait` RPC's long-lived connections), design §4.4, §4.6.

## TD-063: Three CI-only flakes on the 3.12 runner — two failures and a hang

**Priority:** Low
**Added:** 2026-09-17 (session `tdgrind-ao-1`, both on PRs whose diffs did not touch the code under test)

**Status:** Partly done — all three named tests are fixed and PR #192's `-vv` proved itself twice over; the PR #192 hang itself is still unattributed. **A hang now fails with a stack, 2026-09-20 (PR #314, `tdgrind-ao-1`):** `pytest-timeout` with `timeout = 120` and `timeout_method = "thread"`, so the next one is *evidence* instead of silence. It was earned by a second sighting the same day — `tdgrind-ao-2`'s run 35548953938, where 3.13 hung for 14 minutes on a branch touching only `src/agentorc/ui` and two docs; the job's last line was `test_limited_from_one_daily_window PASSED`, and the next test in file order is `test_send_wait_three_outcomes`, the one TD-078 names. That is all a hang leaves: the test *before* it, and a cancel. With the bound it stops in the right file, at the line that is waiting, with **every thread's stack** — which is the only thing that can attribute a wait with no bound. Say what `thread` costs, since it is not an ordinary failure: on expiry it dumps the stacks and `os._exit`s, so the run ends there, with no fixture teardown and the remaining tests unrun. That is the right trade here and `signal` is not, because the hangs this is aimed at are in *threads* — `asyncio.to_thread`, a tmux read, a client waiting on a reply — and a signal can only raise in the main thread: it would fail the test and leave the stuck thread running. A stopped run with stacks beats a cancelled job with none. The bound is per **test item**, setup to teardown, at a tenfold margin over the slowest test here (about 10 s), and it was proved on a deliberate `sleep(300)`, which stops at the line. **The hang itself is still unattributed**, and the next sighting is what will settle it. **What the `-vv` bought (2026-09-17, PR #197):** both 3.12 jobs of that PR hung for the full 15 minutes and the per-test line named the test in one look — a *new* test of that PR, whose `async with server` ends in `asyncio.Server.wait_closed()`. On 3.12 `Server.close()` does not cancel the tasks running the handlers and `wait_closed()` waits for them, so a handler still in `readline()` hangs the run; 3.13 cancels them and passed the same commit in 1m30s twice. Fixed in that PR by tearing the server down by hand. It is **not** the PR #192 hang — that test did not exist then — but it is the same shape, and it is the reason to suspect an `asyncio` teardown rather than tmux for the earlier one. **A fourth flake, found the same way (PR #197, run 35277257855, test (3.12), 1m39):** `test_agent.py::test_derived_entries_go_to_the_record_that_holds_the_directory` failed with `ao-repo-run-1 is idle; kill it first` on its own `remove` — a record it had killed and seen go `exited` was `idle` again. This one is a **bug in the host agent, not in the test**, and is fixed below.

**A pane list older than a kill revived the record it named.** `tick()` reads the pane list in one `to_thread` and the tails in another, then reconciles — and an RPC runs on the loop inside that window. A `kill` there left the tick holding a list that still named the session: `_observe` set `pane` back to True and read a state off the last screen, so the `exited` record came back as `idle`, and `remove` then refused it with *kill it first*. On a fast machine the window is invisible; a loaded 3.12 runner found it. The fix is a `_killed_at` stamp taken by `rpc_kill` and checked in `_reconcile`: a snapshot older than the kill is not allowed to observe that record, and the stamp is dropped as soon as a newer snapshot arrives, so it holds at most one tick's worth of ids. `rpc_close` needs no stamp — a `closed` record is skipped before its pane is ever observed — but it *clears* one, because a `kill` then a `close` inside one tick would otherwise strand a stamp for `CLOSED_KEEP`, which no reconcile would ever reach (review of PR #199). `test_a_pane_list_taken_before_a_kill_does_not_revive_the_record` hands `_reconcile` exactly the snapshot the in-flight tick would have had; without the guard it reports `idle != exited`, which is the CI failure verbatim.

**And why a hang had no evidence at all, 2026-09-21 (found by `tdgrind-ao-2`, built in PR #315):** `LocalClient.call` had **no bound**. Every bound in a test is on the test's own side — `wait_state` at 6 s, each `asyncio.wait_for` at 5 — so a test *cannot* hang inside its own assertions; it can only hang in `await self._reader.readline()`, waiting for a reply that is never coming. That is why the two sightings named a neighbour rather than a line. A call now waits `CALL_TIMEOUT` (120 s, the bound the agent already gives an act over its own link) and then raises **naming the method**, so the next one says which RPC never answered; the calls that mean to block pass their own — `wait` its timeout plus slack, `send --wait` the same — which is the shape `HostAgent._route_act` gives those two between hosts, applied one layer down where the reply is read. And **a call that timed out is not a connection that dropped** (review of PR #315): `AgentStuck` is a subclass of `AgentUnavailable`, so every handler is unchanged, and the one caller that reconnects re-raises it rather than remaking — a wedged agent hidden behind a *nothing changed* at the deadline would be worse than the hang. **It is not only a test fix**: a live worker sitting in `ao send` never came back while its lead read it as `working`.

**Location:** `tests/test_cli.py::test_send_wait`, `tests/test_agent.py::test_the_tick_retires_a_branch_claim_the_session_abandoned`, `tests/conftest.py` (`derived`), `src/sessionorc/agent.py` (`_reconcile`, `rpc_kill`, `_killed_at`)

**Why:** (1) PR #180's first CI run (2026-09-17 ~05:29Z, run 35185832437, test (3.12)): `ao send sw --wait --timeout 5 go` returned `prompt-stalled: … showed no activity within 4.69821 s` against a `hookstub` session — the send path was untouched by that PR, and the job passed on re-run. (2) PR #189's CI run (2026-09-17 ~06:37Z, test (3.12)): the tick had not yet retired a derived `TD-077` `claimed` entry when the test asserted `progress == []`; PR #189 renamed a grant and did not touch `sessionorc.reports` or the tick. Passed on re-run and three times locally. Both are timing-shaped (a bound a slow runner can miss), the kind TD-033 fixed for two other tests by waiting on the real signal instead of a duration.

**Fix:** ✅ both, 2026-09-17 (PR #199), each by waiting on the real signal rather than on a duration or on a task's identity.

(1) `test_send_wait` posted one `working`/`idle` pair on a 0.3 s and a 0.6 s sleep. `rpc_send` captures the revision it waits for **after** `_submit` — a paste, a settle and a composer check — so on a slow runner both transitions can land before that read: the record is idle, its revision is already past, nothing else ever moves it, and the stall window expires. That is `showed no activity within 4.69821 s` exactly. The thread now produces turns *until the send returns*, so whichever cycle lands after the read satisfies both waits at any load, and it ends on idle so the settled state the command prints is unchanged.

(2) `test_the_tick_retires_a_branch_claim_the_session_abandoned` — and five other assertions of the same shape, which had the same latent race — did `tick()` then `await agent._derive_task`. But `tick()` starts a derivation only when `_derive_task` is None or done, and the `agent` fixture runs a live tick loop at `FAST_TICK`: a background tick can already own an in-flight derive whose snapshot predates the `git checkout` the test just made, so the test's own `tick()` starts nothing and the await returns the *stale* answer. The new `conftest.derived(agent, check)` drains an in-flight derive, clears the two caches, ticks, awaits the derive it started, and re-checks — bounded, and a stale derive costs a retry instead of a failure.

**Done when** each has either a deterministic wait or failure diagnostics, and neither fails in ten consecutive CI runs. **Still open:** the PR #192 hang, which no longer has a way to recur unnoticed (the 15-minute cap ends it and `-vv` names it), so the next occurrence closes this entry one way or the other.

**Related:** TD-033 (archived: the same class, two other tests), TD-025 (archived: `test_cli.py` idle-wait diagnostics).

**Why:** it does not. **Across hosts** identity is sound: §4.4a takes a request's host *from the channel it arrived on, never from a field*, and a link is bound to its key. **On one host** the caller is whatever the client puts in the envelope — the CLI copies `AGENTORC_SESSION` from its environment — and the socket, mode `0600`, accepts raw JSON from any process running as the same user, which every session on the host is. So a session can send as **another session** (`AGENTORC_SESSION=<id> ao msg …`) and as **the person** by sending no caller at all (`env -u AGENTORC_SESSION ao msg …`, or the person-only RPCs — `inbox_delete`, and from TD-069 `inbox_snooze` and `inbox_pause` — called directly). `mail.py` already says so in a comment (*the socket takes raw JSON from any local process*), and §4.8 says it of the control gate (*a guard against a confused worker, not a security boundary*); until §4.8a nothing said it of mail's marks or of the person, or what to do about it. The gates were built against **mistakes** — a worker acting on a session it does not control — and they hold against those. They do not hold against a model that decides to lie, and **the `[person]` mark is the most valuable thing to forge**: instructions come from controllers and people (§4.10), and TD-075 puts a cheap model beside a high-trust one that weighs mail by exactly that mark.

**What bounds it today:** anything that can reach the socket already runs as the person's user — it can type into any pane with `tmux send-keys`, edit `~/.agentorc`, or delete the checkout — so this is not a new privilege so much as a quiet, deniable one: forged mail looks legitimate in the record, where `send-keys` does not.

**Options, cheapest first (the anchor recommends 1 and 2 together now, 3 as the real boundary):**
1. **A per-session secret.** The host agent mints a token at launch, puts it in the session's environment beside `AGENTORC_SESSION`, and refuses a `caller` that does not present its own. The person's requests present one the UI and a person's shell hold (a `0600` file). A same-user process can still read another's environment or that file, so this stops the accidental and the casual, not the determined — but it turns *absent caller = person* from a default into a claim that must be backed.
2. **Identity from the channel, as §4.4a already does between hosts.** `SO_PEERCRED` gives the peer's pid; its ancestry names the tmux pane it runs under, and so the session. A `caller` that disagrees with the channel is **refused and shown** — a mark on the card, a line in the person's Inbox — since a mismatch is never innocent. Escapable (a double fork, `tmux run-shell`), so *no ancestry* must read as **unknown**, never as the person.
3. **A real boundary is an OS one.** A session in a container node (TD-057) can reach the home only through its link, so it can only ever be a session of that node; an untrusted model belongs there, with one node per trust level. Tokens and ancestry inside one user account are tamper-evidence, not isolation.

**What option 3 still needs (2026-09-19). What it rests on is the thing TD-077 is about: **nothing on a node's socket tells the person from a session that leaves its `caller` out** — so the reach that was given to the person is given to every session on that node. A container node bounds *which session* a caller can be — the home qualifies it with the link's host — but **not whether it is the person**: a request forwarded from a node with no `caller` is dispatched at the home as the person (`_forwarded`, `agent.py`). So the design round for option 3 has to add: **(a) a node may be declared to carry no person** — an agents-only container — and the home then **refuses every caller-less request from its link**, reads of that node's own records aside; **(b)** on a node that does carry a person, a caller-less `msg` is refused unless every addressee is on that node, and the person inbox is not reachable; **(c) one node per trust level**, since sessions inside one node can still claim each other's ids; **(d)** where the high-trust sessions and the person live — the home, which then runs no untrusted session at all. **The choices, restated (2026-09-19, after the finding above).** What each defends depends on one fact: every session on a host runs as the person's own user, so a *determined* rogue needs no forged mail — it can type into any pane with `tmux send-keys`, which a session reads as its person speaking, and it can call the UI's own API on localhost. Inside one account, identity checks are **tamper-evidence**, not a wall.
- **A. Accept and document.** Write the threat model into the design: the gates stop mistakes, not lies. No work; leaves forged mail looking legitimate in the record.
- **B. Identity from the channel on one host.** Peer credentials give the connecting pid; its ancestry names the tmux pane, so the session. A `caller` that disagrees is refused **and shown** (the card, the Inbox); a caller-less request is the person only from the UI's process or from a process under no agentorc pane, and *unknown* is never the person. Small, and needs nothing from TD-057.
- **C. A per-session secret.** Weaker than B (a same-user process can read it) and redundant beside it. Not recommended.
- **D. A secret only the person holds** (a passphrase behind person-only acts). Closes forged *mail* from the person, and is walked around by `send-keys` into the pane. Not recommended on its own.
- **E. An OS boundary.** Untrusted sessions in agents-only container nodes, one per trust level, **declared to carry no person** so the home refuses every caller-less request from that link; the person and the high-trust sessions on the home, which then runs nothing untrusted. ## TD-091: Nothing says how much context a session has left, or that it has just compacted

**Priority:** Low
**Added:** 2026-09-20 (`tdgrind-ao-1`, from the neighbours survey, TD-059)
**Status:** Open — recommended by the survey, not approved; design first (§4.5a: a card and Focus field) **2026-09-21, Paul: should grinders (and hunters) compact after each TD?** The anchor's answer, pending research: a session cannot run `/compact` itself, so it is a manager's act (`ao send`), not brief guidance; between TDs a grinder's state is all in the ledger, so a fresh run (`ao progress restart`, TD-083) beats a compaction there, while a hunter's state is what it has explored, so compaction suits it better; per-TD is too often for either; and **the missing piece is this entry's signal** — with the context's size on the record, the rule is a manager's: *at a task boundary, past a threshold, restart a grinder or compact a hunter*. (2) a compaction is **an ordinary model call over the whole context**, and what decides its price is whether the cache is warm: a cached read is a tenth of base input, a five-minute cache write 1.25×, a one-hour one 2×, and the cache lives five minutes unless the longer one is asked for; (3) **on a warm cache, compacting beats both carrying on and a fresh start on tokens** — the break-even is about five further turns at 40k of context, two at 100k, fewer beyond — and **a fresh start is never the cheaper one on tokens while the cache is warm** (its re-read of brief and docs is an uncached write, and it lands at a larger context than a summary does): *the anchor's first answer above had this backwards — a restart's case is quality and a clean head, not price*; (4) **idle time turns it round**: past the cache's lifetime the whole context is paid for again at full price on the next turn, so compacting a *cold* 100k context costs about twice a fresh start — **compact before a long wait (CI, a reviewer, the anchor's merge queue), not after it**; (5) quality: Anthropic names *context rot* and advises compacting at a clean boundary, warning that an aggressive summary loses what only later turns out to matter — so a **hunter**, whose state is what it has explored, is compacted at a pause and never restarted mid-investigation, and a **grinder**, whose state is in the ledger, may be either; (6) `PreCompact` and `SessionStart` with `source: compact` are the hooks around it — the second is how state is re-injected after one, and is already read here (TD-090) — and reports disagree on whether `PreCompact` fires for an automatic compaction; the automatic trigger's threshold is set by environment (`CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` and others), its default not documented. **What it suggests as configuration** (per profile, since windows and prices differ): a context threshold past which a session is compacted or restarted *at a task boundary*, and an idle length past which it is compacted *before* the wait; the ordering — boundary, then expected idle, then the raw threshold — is policy, not configuration; the act is its manager's (`ao send "/compact"`, or the restart rule). **What is not observed yet**: this entry's context size and `compacted_at`, and any notion of *about to wait* — the host agent knows a session is idle, not that it is about to be. On a subscription the unit is the usage window rather than dollars; the ratios hold.
**Location:** `src/agentorc/adapters/claude_code/` (the transcript under `~/.claude/projects/`, which the adapter already reads for the model), the record, the card and Focus header; design §4.2, §4.3 (an optional adapter capability), §4.5a

**Why:** a session near its context limit is about to compact, and one that has just compacted has lost most of what it knew — the two moments a lead reading a quiet worker, or a person deciding whether to trust a long-running session's next step, most wants to know about. agentorc shows a model and each profile's usage windows and nothing about context. `tallu-wonder/agentboss` reads it from the transcript: the context in use is the last non-sidechain usage record's input + cache-creation + cache-read + output tokens, and a `type: "system", subtype: "compact_boundary"` record's `compactMetadata.postTokens` resets it until the next turn ([ADR 2026-09-20](decisions/2026-09-20-session-desk-neighbours.md)). **Done when** a Claude Code session's card shows its context in use, and a compaction is visible on it within a tick.
